## 3. 跨篇界 Block 修复（§24–§26）

### 3.1 病因有两个，只修一个不够

`passages.section` 只标在标题行上、不向下传播，正文行的 `section/subsection/ab`
三列全是 NULL，于是 `_boundary_key` 对所有正文行返回 null，相邻两篇在判断上「同段」。

实测（`之`，standard，9,905 块，扩容前）：

| 修法 | 跨篇界块 |
|---|---|
| 只修 `_row_key`：用 `sections.first_row` 区间表给无键行回填篇名键 | 130 → **106**（只消除 18%） |
| 再加 `_fit_hi` 合并接缝判定 | 106 → **0** |

大头在**合并环节**：块是被「装到长度上限为止」撑大的，撑大的那一截从没经过
`_can_take`。所以第二步是在 `_fit_hi` 的接缝上补做同一套判定——两侧证据不衔接就断开。

### 3.2 验收改成正向断言

旧的 `test_known_limit_blocks_may_cross_section_boundary` 只断言「别超 5%」，且只看
首页 100 块——130 → 106 这种半吊子修复照样绿。现在断言 **`cross == 0`**，且样本是
**全部块**（一次性组装，不走分页）：

```
之 75,766 命中 → 42,165 块
大夫 3,531 → 2,994 块
齊桓公 151 → 126 块
合计 checked = 45,285 块，cross = 0
```

### 3.3 代价（§26 事先确认接受）

史記/國語的块从「段」粒度变粗到「篇」粒度：`_can_take` 的 `# src:` 闸门对这些书
永久关闭，因为回填的篇名键与出处块键不再相等。**Passage 本身一个字没动**——
`row_first/row_last/passage_ids/text` 全部来自原文，变的只是分组。

## 4. 戰國策 Section（§14）

计划书设想的是「秦策一/秦策二」式编次。**实测这个底本（SBCK 鮑彪校注本）没有这种
编次**——实际结构是「卷第一~卷第十，每卷一个国别」，国别标题行在每卷正文第 5 行
（`　東周(漢志河南鞏東周君所居…)¶`），而旧正则 `ZHANGUOCE_SECTION_RE` 要求 `\s*$`
结尾、该行以 `¶` 结尾，因此 **0 命中**。

修法（三处，全部入规则表）：

1. 行尾 `¶` 容忍；
2. 国别标签只取括号前的国名（`東周(漢志…)` → `東周`），不再整行截断；
3. 只认**每卷正文的头一个**国别标题——实测同一文件里 `齊(彪謂…)`（:004 第 150 行）、
   `秦(按此則…)`（:004 第 706 行）是行内注被切出来的片段，不是标题。

结果：戰國策 sections **0 → 12**（東周/西周/秦/齊/楚/趙/魏/韓/燕/宋/衛/中山），
juans 10，覆盖 12,856/13,220 = **97.2% OK**。如实报告：「秦策一」式细分在本底本不存在，
这是用词与底本不符，不是覆盖缺口——`preqin.json` 的 neg-04 注里写明了这一点。

## 7. Manifest、Coverage Audit 与「加一本书」的流程（§17–§18、§23）

### 7.1 两份派生产物

`scripts/pipeline/manifest.py` 产出 `data/metadata/corpus_manifest.json` 与
`section_coverage.json`。它们**含真实书名，只待在 `data/`**——`build_artifact` 的
`EXCLUDE=["data"]` 挡住，绝不进 `_site`（发布闸门①也会立刻拒绝）。

### 7.2 coverage 的口径：不是「越高越好的装饰指标」

section 用**区间模型**：一条 section 覆盖本文件内自 `first_row` 起至下一条 section。
缺口三类成因，报告里点名不粉饰：

- **结构使然**：卷首署名、總目、四庫叢書题，每文件一两行，清不掉也不该清；
- **源转录缺卷首题**：國語 003/007 的首行直接是正文，卷名只在卷末版心题里，
  整卷（1,129 行）无所归——只有源文件能解释；
- **篇题识别失败**：这才是要修的 bug，也正是本阶段修掉的三处 WYG 问题。

判据与 `api/db.py` 的 `list_books` **逐字一致**（同一套 status，页面与审计表给同一个答案）：
`FAIL` = 正文行 > 0 却一条 section 都没有；`WARN` = 覆盖 < 90%；其余 `OK`。
本次：**6 OK / 1 WARN（國語 86.3%）/ 0 FAIL**，7 部书全部入 FTS 索引。

### 7.3 「加一本书」不再靠记性

加书最容易漏的一步是：书进了库，而 `check_publish.REAL_TITLES` 没跟着加——那个
「产物里出现真实书名就拒绝发布」的闸门，对新书就是形同虚设（本阶段补过一次
前漢書/後漢書）。所以 `manifest.py` 里加了 `publish_gate_sync`：拿语料书名去和
`REAL_TITLES` 对账，`REAL_TITLES` 是唯一真源，这里只对账、不复制一份。审计表现在
每次都打印「发布闸门书名清单：与语料一致」。

## 9. 本轮顺手修掉的两个真 bug

### 9.1 `zh.py`：Windows 转换 API 被喂错了长度参数（**有效**）

`LCMapStringEx` 的 `cchSrc` 数的是 **UTF-16 码元**，而代码传的是 Python 的 `len()`
（**码点**数）。含星形汉字（扩展 B 的 𫝊 U+2B74A、𤣥 U+248E5——正是 WYG 篇题里那些字）
的串会被截断：每个星形字少算 1 个码元，**尾部字符被整段吞掉**。实测：

```
'a𫝊b龍'          → 'a𫝊b'            （龍 没了）
'漢書敘𫝊第七十下'  → '汉书叙𫝊第七十'   （下 没了）
'𫝊'              → '\ud86d'          （孤立代理项：非法 Unicode，长度还是 1）
```

危害有两层：检索词被截断 → **静默少命中**；转换结果含孤立代理项 → `dual_text` 的
「长度不变」闸门拦不住（长度恰好相同），会把非法 Unicode 当作「简体」发出去。
本阶段之前的处理是「JS 侧照抄这个行为以求一致」，并记下实测：203,308 条正文里
1,176 条含星形字、1,172 条因长度变了而回退、**4 条不回退**——那 4 条就是问题本身。

修法是传 UTF-16 码元数。修完之后 380,446 条正文的简体转换 **回退数 0**
（此前 1,176）、全部 9,508 个单字/多字样本 Python 与 JS 逐字节一致。星形字样本
（`漢書敘𫝊第七十下` 等）已加入 `check_engine` 的固定样本，这类回归不再靠
「样本里别出现星形字」来回避。

### 9.2 三类「写死数字」的测试（**有效**）

扩容必然打破写死的计数，但不该以「每次加书都去改一遍数字」收场——那等于把验收
悄悄关掉。本轮把三处改成**只在缩水时才失效**的判据：

| 位置 | 原写法 | 现写法 |
|---|---|---|
| `test_e2e.py` | `len(parsed_*.jsonl) == 5`、`files == 118` | 从正式库导出 `N_BOOKS`/`N_FILES` 当基准 |
| `test_result_block.py` | `total == 74`、`(85, 62)` | `block ≤ hit_total`、`short.total > long.total` 等关系式 |
| `test_phase4_questions.py` | 探针词 `董卓`（已进语料，157 处） | 改成 `姜維`，并断言探针词**必须不在库**，进库即报警 |

另有 `recall.py` 的自检探针词（原用董卓）同样处理：`SELFTEST_ABSENT = "坑儒"`，
运行时校验；并修掉一个更深的毛病——**自检失败原先不影响退出码**（`run()` 照样返回 0），
现在自检不过整次跑分即失败。

### 9.3 `test_result_block.py` 里那条「绿在 bug 上」的用例（**有效**）

`test_section_dedup_marks_both_without_duplicate` 原先指望「正文块与篇名块合并成
`both`」。修复跨篇界后它红了——因为那个 `both` 正是**跨篇界的产物**：正文块不受篇界
约束、一路合并到装够字数，跨过篇题把下一篇的篇首也吞进去，篇名锚点恰好落在块里。
现在拆成两条：同篇内的撞车仍标 `both`（`dedup_same_section_db`），跨篇的则断言
**两个块各归各篇**（`test_section_dedup_does_not_bridge_two_sections`）。

## 12. 性能（§27）

`tests/perf_corpus.py` 进程内直调 `search_result_blocks`，每个查询跑 5 次取 min/p50，

降频且不恢复，不把「机器变慢」误判成「语料变大」。

**这两张表不能直接相减**，必须说清楚：扩容前那一轮的**对照小查询自己漂移了 +96%**
（81ms → 159ms），也就是说机器在那轮里已经降频，越靠后的查询被抬得越高。扩容后这一轮
对照稳定（−6%），数字可信。

于是前表的每个数只能给一个**区间**（除以 1.0~1.96 的漂移），而不是一个真值：

| 查询 | 前表实测 | 前表折回区间 | 后表实测 | 后/前的倍数区间 | 命中倍数 |
|---|---:|---:|---:|---|---:|
| 齊桓公 | 82ms | 42–82ms | 162ms | ×2.0–3.9 | ×1.6 |
| 管仲 | 84ms | 43–84ms | 168ms | ×2.0–3.9 | ×1.9 |
| 將軍 | 355ms | 181–355ms | 1,065ms | ×3.0–5.9 | ×3.5 |
| 大夫 | 956ms | 488–956ms | 1,658ms | ×1.7–3.4 | ×2.4 |
| 曰 | 2,598ms | 1,326–2,598ms | 3,630ms | ×1.4–2.7 | ×3.8 |
| 王 | 2,593ms | 1,323–2,593ms | 3,154ms | ×1.2–2.4 | ×1.8 |
| 之 | 4,523ms | 2,308–4,523ms | 3,911ms | ×0.86–1.7 | ×2.3（块 ×4.3） |

（前两个查询排在最前，跑时对照还是 1.0x，所以那两行的区间下沿最接近真值——
**轻查询确实慢了约 2 倍**，162ms 的绝对值仍可接受。）

站得住的结论只有三条，别的都是过度解读：

1. **耗时随命中数**近似**线性、不爆炸**：重查询命中涨 1.8–3.8 倍，耗时涨的倍数在
   任何一段区间里都被命中倍数压住或相当（`曰` ×3.8 命中 → 至多 ×2.7 耗时）。
2. **最坏情况有界**：全库最重的查询（单字 `之`，75,766 命中 / 42,166 块）**3.9 秒**
   返回，峰值内存 501 MB，没有卡死、没有 OOM、没有超时。
3. **多关键词查询几乎不受扩容影响**（13ms）：这是索引选路正确（`fts` 而非 `like`）
   的直接证据；§29「不许上向量库/RAG」并没有被性能问题逼退——高频词走的是 FTS5
   trigram + bigram 两条既有索引，本阶段没有新增任何索引或依赖。

顺带一个反向发现：**轻查询的绝对耗时翻倍**（齊桓公 82→162ms），而它的命中只涨 1.6 倍。
这不是本次改动引入的——同样的库、同样的代码路径，扩容后每页要组装的块更多——但它说明
`result_block` 组装对语料规模是**线性**的，下次再翻倍（14 部书）时这一档会到 300ms 上下，
应当在那之前考虑 §14 建议的组装缓存。

未被验证的部分也如实写明：**浏览器端**渲染 42,166 块的分页交互没有实测（见 §13.4）。

## 13. 已知问题

### 13.1 `list_books` 约 350ms — `注意`（**既有**）

`_BOOK_AGG` 是扩容前就有的慢点，本次扩容后绝对耗时上升（书数 5→7），但仍在
可接受范围（首页一次请求）。不做优化，如实记录。

### 13.2 高频词整段组装每次翻页重跑 — `注意`（**既有**）

数据库层分页仍未做（第六点一阶段已记录）。`之` 每翻一页要重跑一次 3.9 秒的组装。
本阶段未改，原因同前：改它要动组装结果的定义，风险大于收益。

### 13.3 WYG 行内注让「待确认」从 17,347 涨到 79,713 — `注意`（**新**）

颜师古/章怀太子的行内注约占 WYG 两书 36% 字符，切成候选记录后全库 `pending_commentary`
从 17,347 涨到 **79,713**。原文一字未删（`text_orig` 就是原文），但检索片段里仍会
看到括注——这是第六点一阶段 §19B 未解决问题的放大版。**不算失败**：切片正确、
可人工逐条检查，但「自动裁掉注者、只留正文」没做。

### 13.4 浏览器端的块渲染未实测 — `注意`（**新**）

`_site` 产物、API 契约、演示模式横幅都有脚本化验证（`check_engine` ⑬⑭），
但「浏览器里点开 `#/coverage`、翻到 `之` 的最后一页」这类**交互**没有自动化，需要人工过一遍。
本阶段新增的页面在此列。

### 13.5 别名不会自动解析 — `注意`（**既有，符合设计**）

`刘邦` 0 命中 / `高祖` 585、`王政君` 0 / `元后` 44、`刘秀` 9 / `光武` 705、
`汉武帝` 8 / `武帝` 877。系统不猜别名（§八.4），这些用例在 `qin_han.json` 里
**明写为负例并指向对应正例**，而不是假装能查到。

### 13.6 同形异义与同名词 — `注意`（**新**）

- `元后`：前漢書/後漢書 指元帝皇后王政君，尚書「元后作民父母」是另一个意思；
- `河西`：戰國策 指魏地，漢書 指河西走廊。两处都是真实语料，不合并、不消歧。

### 13.7 國語 003/007 覆盖不到 — `注意`（**既有**，源文件如此）

两个文件首行直接是正文、卷名只在卷末版心题里，整卷 1,129 行无所归。不硬凑一个
section 出来，manifest 里点名。

## 14. 下一阶段建议

1. **浏览器端自动化**：把「点开页面 → 翻页 → 断言渲染」做成脚本（Playwright 之类），
   否则每阶段的交互验收都要人工兜底。
2. **行内注的取舍**：79,713 条 `pending_commentary` 需要一个可判定的裁切规则
   （如「注者名前缀 + 括号配对」），否则检索片段会越来越吵。
3. **组装缓存**：`之` 这类查询的组装结果在同一请求序列里可以复用（翻页时命中集合不变）。
   这是 13.2 的低风险解法。
4. **继续加书**：`manifest.py` 的审计 + `rebaseline_cases.py` 已经就位，下一批
   （三国/晋/隋唐）可以直接按 §7.3 的清单跑；预计新的家族差异会在
   `structure.py` 的 overrides 表里出现，**不要再往代码里加书名分支**。
