## 1. 本阶段目标

用户可以直接用自然语言提问，系统理解其中的人物与意图，从真实古籍里把**能够回答
这个问题的完整史料片段**找出来，按事件聚合，并把不同史书的记载并排摆出来。

流水线：

```
用户问题 → 问题分析 → 实体识别 → 意图识别 → 古代表达扩展
        → 候选史料召回 → 相关性排序 → 完整史料片段 → 事件级聚合 → 不同史书对照
```

**本阶段不做的事**（任务书 §2.3）：不生成答案、不摘要、不改写、不翻译。系统只
回答「哪些史料在讲这件事」，不回答「这件事是什么样的」。后者是第五阶段。

第一验收问题（§31）「齐桓公什么时候死的？」的完整链路：

```
识别   齊桓公 + death
扩展   齊桓公 桓公 小白 | 卒 薨 崩 沒 歿 殁 弑 卒於 … | 死 終 亡 殺（弱）
召回   实体池 449 条
排序   实体命中 14 + 意图命中 8 + 同段共现 15
聚合   15 个事件 / 33 个片段
来源   春秋左傳 · 史記 · 國語
首位   左傳「因寺人貂以薦羞於公…冬十月乙亥，齊桓公卒。」
```

## 3. 数据库变化

**表结构：只加了一张窄表，不动任何已有表、不动任何原文。**

```sql
CREATE TABLE src_paragraphs (
  file_id        INTEGER NOT NULL REFERENCES files(file_id),
  row_no         INTEGER NOT NULL,   -- `# src:` 所在行
  paragraph_code TEXT NOT NULL       -- 段号前两级，如 '68.1'
);
```

**为什么加（§19A 要求先 profile）**：Phase 3 的 `result_block._FileCache.segments()`
每次检索都要按文件取段落区间，原做法从 `passages` 读全部 `source_ref_json` 再逐条
`json.loads` + 正则 —— 实测 6 个大文件 **56.1ms**；换成这张无宽列、走索引的窄表后
**3.3ms**，快 17 倍，省下的时间占一次完整查询的 40% 上下。

**一致性保障**：`paragraph_code` 由建库时调用 `search.result_block._src_paragraph()`
算出 —— 与检索侧**同一个函数**，不存在两套口径。不需要保存 code 为 NULL 的行，
因为 `segments()` 对它们本来就是 `continue`。

**行数**：`src_paragraphs` 11,200 行；`passages` 224,822 行（未变）。

**`schema.sql` 与 `sqlite_store.SCHEMA` 的镜像关系**：本阶段发现两者在加入
`src_paragraphs` 后不再一致（`sqlite_store.SCHEMA` 是运行时真源，`schema.sql` 是
给人看的镜像，README 第 41 行声明了「与 sqlite_store.SCHEMA 镜像」）。已补齐，
并用脚本逐条比对确认：**15 条语句，两边完全相同**。

**没做的事**：没有迁移脚本、没有 ALTER TABLE、没有给 `passages` 加列。全量重建
（`run_all.py`，约 15 秒）即可得到新表。

## 4. question analysis 设计（`search/question.py`）

输入一句自然语言，输出一个确定性的 `Question`：繁简统一后的文本、实体列表、
意图列表、纪年、时长标记、以及**每一步的说明**（`notes`，进 API 响应供复核）。

**4.1 繁简统一先行。** 用户多半打简体，语料是繁体。先把问句整体转成繁体再往下
走，后续所有匹配只面对一套字面。用的是 `search/zh.py` 的系统字符表（`LCMapStringEx`，
零依赖，失败恒等回退）。转换**长度不变**，这一点被当作可靠性判据：长度变了就整体
回退到原文，不冒险。

**4.2 实体识别。** 长词优先做交替匹配，所以「齊桓公」不会被「桓公」吃掉。识别不
出来的短称**不硬认**（§八.4）—— 「桓公」单独出现时，实体栏就写「桓公」，不补成
「齊桓公」。

**4.3 意图触发。** 意图表同时带**问句触发词**（`ask`）和**语料表达词**（`corpus` /
`corpus_weak`），两者是耦合的：`ask` 放松，`corpus` 就必须收紧，否则误报会灌满
召回池。本阶段实际踩到的坑：

> 「怎么」曾经放在 `flight`（流亡）的 `ask` 里，于是「管仲是怎么死的」同时触发
> death 和 flight 两个意图。把「怎么/如何」从 flight 的 `ask` 里去掉之后，「法/令/政」
> 才敢放回 `corpus` 的强词档 —— 否则「商鞅变法」会被「怎么」这种虚词带偏。

**4.4 意图表的中文写法。** 词表全部来自**语料实测频次**，不是外部词典。以 death 为例：

| 档 | 词 | 判据 |
|----|----|------|
| 强词（可独立召回） | 卒(2307) 薨(259) 崩(342) 沒(107) 歿(7) 殁(2) 弑(20) 卒於 卒于 死於 死于 卒之歲 卒之岁 | 基本只用于「死」 |
| 弱词（只排序不召回） | 死(2540) 終 亡(1680) 殺(2352) | 更常用于别的意思 |

「歿/殁」是任务书 §31 点名的扩展词，语料里确实有（歿 7 段、殁 2 段，全是「死」），
按「说不清出处的词不写进结果」的标准够格，本阶段收进强词。

**4.5 排除用法。** 「亡」全库 1680 次里多数是**灭亡/逃亡**（追亡人、必亡、存亡之），
不加排除的话「重耳流亡了多少年」会被判成 death。`exclude` 表按**紧邻的搭配词**
排除（流亡/出亡/亡奔/逃亡/亡命/亡歸…），不做语义猜测。

## 5. query expansion 设计（`search/query_expansion.py`）

**只生成检索词，不生成史料。** 每个词都能在语料里查到实际出现，查不到的词不进结果。

**5.1 为什么要分组。** `engine.run_search` 把多个词按**空格连接 = 隐式 AND** 处理。
把「管仲 卒 薨 死 沒」拉平成 AND，要求同一段同时含这四个词，命中几乎为零 ——
所以必须是：

```
(管仲 OR 管夷吾 OR 管子)   ← 组内 OR
    AND
(卒 OR 薨 OR 崩 OR 沒)     ← 组间 AND
```

**5.2 实体词的三档**（`_term_roles`，依据是实体层自己的证据结构，不是按下标取）：

| 档 | 例子 | 分 | 判据 |
|----|------|----|------|
| `entity` | 晉文公 | 14 | 规范名 |
| `alias` | 重耳(198 段) 小白 管夷吾 | 6 | 已核实别名，且语料里真的有 |
| `weak` | 文公 穆公 夷吾 | 2 | 短称 / 多家共用，裁决不了 |

按下标取档曾经是错的：重耳从不写成「國名+爵位+名」形态，按语料全称表分类会把它
打成弱候选，「重耳居狄凡十二年而去」这种**答案段落**就沉到了「魯僖之二十五年」后面。

**5.3 共享别名降档。** 一个称谓只要**可能指的人不止一个**，就不算确定别名。判据
直接取实体层那份唯一的分布（`short_forms`，已核实别名已折入其中）：

```python
return {al for al, dist in entities.short_forms().items() if len(dist) > 1}
```

踩过的坑：只看已核实表是不够的 ——「桓公」在已核实表里只挂在齊桓公名下，但语料分布
是 齊桓公 94 / 魯桓公 12 / 鄭桓公 7 / 秦桓公 7 / 杞桓公 7 / …共 15 家。漏掉这一层，
史記「考王封其弟于河南，是為桓公…桓公卒」这段**東周**桓公就会蹿到第 4 位
（实测 rel=29.0，仅次于是齊桓公本人的几段），而正文里根本没有「齊」字。

**5.4 用户原词加权。** 用户在问句里**实际写下的**称谓（「重耳」而不是规范名「晉文公」）
命中时按精确命中计分，不是按别名。这不是新增同义词，只是承认用户的原词就是最精确的
检索词。

理由是一条实测反例：问「重耳流亡」时，國語「敗於城濮懼出奔楚…晉文公討不伏」讲的是
**衛成公**出奔，却凭「晉文公 + 奔」压过了「重耳出奔」那一句。原词加权后，「重耳」
的原文升到第 1 个事件。

**5.5 兜底主题词。** 问句里没有人物实体时（「城濮之战谁赢了」），把问句里的实词
切出来当主题词 —— 宁可少切，不可乱切：切错了就是替用户编问题。

## 6. entity 设计（`search/entities.py`）

**核心原则：实体从语料自身派生，不硬编码，不猜。**

**6.1 两张表，一份分布。**

- **已核实表**（8 个实体，人工看过原文、带 `evidence`）：齊桓公 / 晉文公 / 秦穆公 /
  晉惠公 / 管仲 / 商鞅 / 鮑叔牙 / 百里奚。
  别名栏留空的（百里奚）表示**语料里找不出可靠的互指证据** —— 宁可只认全称，
  也不把「史书上一般这么说」写进来。
- **语料派生**：全称 674 个（「國名+谥号+爵位」形态）、短称 253 个。

两张表**折成同一份分布**（`short_forms`），而不是各留一份 —— 否则会出现两套口径打架：
`_AMBIGUOUS` 说「桓公」只有齊桓公一个候选，语料分布却说有 15 家。

**6.2 短称怎么区分「真爵称」与「巧合」。** 语料里「侯使」「公曰」「子伐」这类
两字组合是散文跨词边界的巧合，不是称谓。判据取**至少被一个全称佐证过**
（存在「齊桓公」才认「桓公」）：

> 实测：单靠「独立出现占比」不行（文公 98.5% vs 侯使 98.3%，几乎一样），
> 单靠频次也不行（侯使 58 次，比真名的 鄭莊公 13 次还高）。

**6.3 `bare_hit`：短称必须独立出现。** 语料里「鄭穆公之子」也含「穆公」，但它写的
是鄭穆公，不是秦穆公。判据只看**紧邻的前一个字**：是国名字就是在组成别人的全称。
中山是双字国名且「中」「山」单用太常见，**不放进**国名字集合 —— 宁可漏判，不可错杀。

**6.4 性能。** `occurs_in_corpus` 带进程内缓存（不加缓存时每个别名每问一次就要全表
扫描 40ms）；`_corpus_scan` 用 `lru_cache` 全库只扫一次。

## 7. ranking 设计（`search/ranking.py`）

**纯打分排序，不做文本加工。** 每一项都能对着一条真实命中说明白，逐项记进
`detail` 并随 API 返回，验收时可复核。

| 打分项 | 分 | 说明 |
|--------|----|------|
| 实体精确命中 | +14 | 问「齊桓公」，段里就写着「齊桓公」 |
| 第二个实体 | +9.5 | 第二个人也写着 |
| 实体别名命中 | +6 | 写的是「重耳」；只在没有规范名命中时才计 |
| 用户原词命中 | +14 | 用户自己写的词，按精确命中算（见 §5.4） |
| 实体候选（短称） | +2 | 语料裁决不了的短称，只是个候选 |
| 意图强词命中 | +8 | 段里有「卒/薨/崩/沒」 |
| 多意图词 | +2/个 | 收益递减，封顶 +14 |
| 意图弱词 | +1.5/个 | 封顶 +4.5，且**不触发**共现加成 |
| 实体+意图同段 | +15 | 最强的相关性证据 |
| 候选实体+意图同段 | +6 | 「是不是这个人」没定论，只给一半多 |
| **多实体同段** | **+20** | 问 A 与 B 时两位都写着；**按全部写法判** |
| 只有实体没有意图 | +3 | 相关，但不是问的那件事 |
| 时长年数 | +20 | 问「多少年」时，「凡十二年」就是答案 |

**7.1 弱意图词不能触发共现加成。** 「子」「君」「殺」遍地都是，拿它当同段证据等于
没证据 —— 否则「秦穆公以夫人入公子夷吾為晉君」会被顶到真正的「秦穆公与百里奚同段」
之上。

**7.2 多实体同段必须按全部写法判。** 本阶段修掉的一个**说错话**的缺陷：

> 语义上「秦穆公和百里奚」的同段判定原本只看规范名「秦穆公」，而语料里写的是
> 「秦繆公」（缪公正是秦穆公的已核实别名）。于是系统对外宣称
> **「语料中没有任何一段同时写着 秦穆公 与 百里奚」** —— 假的，语料里有 2 段
> （「昔繆公求士…東得百里奚於宛」，諫逐客書）。系统可以少说，不能说错。
>
> 修法：同段判定改用**每个实体的全部写法**（短称仍过 `bare_hit`，不至于把「鄭穆公」
> 算成秦穆公）。修完「管仲和鲍叔牙」的第一位也换成了史記「鮑叔牙曰…君將治齊」
> —— 那才是正面记载两人关系的段落。
>
> 同一条判据也用在召回说明上：有同段就报「语料中有 N 段同时写着 A 与 B」，
> 没有就报「没有任何一段同时写着」；池子被截断时**不敢下否定结论**，只说清检索范围。

**7.3 相关度不是可信度。** 前端明确写了这句话：分数只用于排序，不是对史料可信度的
评判。不同史书的记载**从不合并**，因为合并等于替用户裁决史料异同（§八.4）。

## 8. event aggregation 设计（`search/aggregate.py`）

**事件边界不重新发明。** Phase 3 的 `result_block._expand` 停止条件（同文件 /
结构键变化 / `# src:` 段 / layer / 硬上限）已经定义了「一段可读的史料」，本阶段
只做两件事：**贴上第四阶段的相关度**、**按书聚类**。

**8.1 聚类。** 按（文件 + 结构键）把片段归到同一个事件；结构键缺失时退化为文件内
窗口（`CLUSTER_GAP = WINDOW_HARD_CAP // 2`）。

**8.2 修掉的丢片段缺陷。** Phase 4 第一版 40 个命中只组装出 17 个片段。原因是
Phase 3 的 600 行窗口上限会**静默跳过**同一文件里相隔较远的命中
（`pos.get(pid) is None: continue`）。加了 `_cluster()` + `_dedupe()` 之后片段升到 30，
左傳里「管仲卒」那几段回来了。这是本阶段最严重的一个 bug。

**8.3 去重只做包含，绝不做并集。** 两个片段相交时，只保留包住对方的那个；**不拼接**
两个片段的文本 —— 拼接会造出原文里不存在的连续文字，那就是伪造史料。

**8.4 跨书永不合并。** `sources` 按书分开列出，是**并排**呈现，不是物理合并。

**8.5 排序。** 事件按 `(-相关度, 最佳命中排名, -命中数, book_id, file_id, 起始行)`
排。第二键用「最佳命中排名」而不是命中数：曾经因为按命中数排，一个 15 处命中的
史記片段把写着「冬十月乙亥，齊桓公卒」的那段压到了后面。

**8.6 诚实说明不省略。** 语料里没有就是没有（见 §10 董卓例），两人从未同段就明说
从未同段，并把同段段数一并报出。

## 9. 繁简双轨设计（`search/dual_text.py`）

**一句话：原文永远只有一份，简体是**另存**的一份副本。**

```python
def simplify(text) -> dict:      # {"text", "ok", "changed"}
```

- 转换用 `search/zh.py`（系统 `LCMapStringEx`，zh-CN，零依赖，失败恒等回退）。
- **长度不变**被当作可靠性硬判据：长度一变就整段回退到原文，并置 `simplified_ok=False`。
- 前端与 API 用的是**同一个**转换函数，两边不会出现两套简体。

**契约（§2.2 的落地）**

| 字段 | 内容 |
|------|------|
| `text` | 永远是 `text_orig`，一字不改 |
| `text_simplified` | 派生副本，**只在 `text=simplified\|both` 时才出现** |
| `text_mode` | `orig`（默认）/ `simplified` / `both` |
| `simplified_ok` / `simplified_chars` | 转换是否成功、动了几个字 |

**没有做的事**：简体不写回数据库、不覆盖 `normalized_text`、不改 `text_orig`。
测试 `test_simplified_keeps_orig` 直接断言 `text_simplified == simplify(text)` 且

## 16. 第五阶段建议

1. **让 AI 基于召回结果作答（这才是第五阶段）**。第四阶段已经把「能回答问题的
   史料」找出来了，第五阶段应该：把 `aggregation.events` 作为**唯一输入**交给模型，
   要求每句结论都能指回 `block_id` / `passage_id`，并在回答里保留原文引用。
   绝不能让它自由发挥 —— §2.3 的红线在第五阶段依然是红线。
2. **把「不同史书对照」做成显式能力**。现在 `sources` 只是并排列出，第五阶段可以
   做**异文对照**（同一事件在左傳/史記/國語里的记载差异），但差异必须由人裁决，
   系统只呈现并列，不下「谁对」的结论。
3. **补事件名词表**，解决「城濮之战」这类无人物实体的问句（§15.4）。
4. **做 §19B / §19C 的收尾**：SBCK 括注需要可靠结构才能裁决，section_ref 需要先
   定统一语义。两件都不能靠猜。
5. **问答模式加过滤参数**（book/edition），与第三阶段对齐。
6. **光杆短称的交互引导**：「桓公」这类问句，返回结果时同时提示「可能是齊桓公、
   魯桓公、秦桓公…，请补上国名」，而不是只丢 33 个事件给用户（§15.7）。
7. **性能**：目前 125~200ms，还有空间。可考虑把 `_corpus_scan` 的产物（全称/短称
   分布）在建库时落成表，省掉每次进程启动后的首次扫描。
