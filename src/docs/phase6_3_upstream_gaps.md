## 怎么查的（可复现，只读）

三条互相独立的证据，不一致就不下结论：

1. **上游自己声明的范围**：读每本书的 `Readme.org`「目次」，取最后一条**非「考證」**
   的卷目 —— 这份目次是 Kanripo 数字化时按文件生成的，它到哪一卷，正文就到哪一卷。
2. **文件数**：`ls HistoryLibrary/kanripo/<book>/*.txt | wc -l`。
3. **库内篇名**：最后一个正文文件的 `sections` 篇名是什么（`列傳第十四` 之类）。

```bash

# ① 上游目次末条（以 北齊書 为例）
PYTHONIOENCODING=utf-8 python -c "import io,re;t=io.open('beiqishu/Readme.org',encoding='utf-8').read();\
print([l for l in t.splitlines() if '卷' in l and '考證' not in l][-1])"
#   → - [[file:KR2a0021_035.txt::035-1a][卷三十五]]

ls beiqishu/*.txt | wc -l        # → 36（_000 目錄 + _001.._035 正文）
```

三國志／晉書 的对照同样成立：三國志正文文件 `_001.._030` 的篇名依次是
`魏志卷一`…`魏志卷三十`，再往下没有文件；晉書 `_031.._033` 是
`列傳第一`/`列傳第二`/`列傳第三`，之後没有文件。两书的 `Readme.org` 目次也分别
止于「卷三十」「卷三十三」，条目**没有**「魏志／蜀志／吳志」这类前缀（所以不是把
三部编号压扁造成的假象）。

**换个分支解决不了**：`WYG` 分支与 `master` 的文件集**完全相同**（北齊書两分支都是
37 个文件，Readme 目次同样止于卷三十五；隋書 51 个、北史 24 个，同理）；`_data`
分支只有 `imglist/`（书影清单），不含更全的正文。即：这是上游数字化的范围，
不是我们拉错了分支。

## 两处「虚警」（方法上的教训，记下来免得下次重犯）

机械地按「卷 + 数字」解析卷题标签，会在两个地方报出**假缺口**：

- **魏書**：报缺 卷一百五、卷一百八。逐文件核对后：`KR2a0020_105.txt` 的文件头写的是
  `#+PROPERTY: JUAN 前上十志啓`（是「十志」前的啓，本身不是卷），`_108.txt` 写的是
  `#+PROPERTY: JUAN 卷一百八之一`（「之一／之二」写法，且卷题只出现在**文件头**，
  不在正文行里）。→ 魏書 114 卷并不缺。
- **北齊書 的「重号」**：卷题同时出现在目錄文件 `_000`（50 条）与正文文件（44 条），
  `juans` 表因此有 94 条记录。这是**同一个卷被记了两次**，不是重复入库。

教训：判「缺」必须落到**文件与正文行**上，只看计数会两头出错（一边虚报缺、
一边把重复计数当成缺）。

## 对系统的影响

1. **检索能力**：无影响。已入库的正文都能搜到、能定位；召回 360 例 0 失败。
2. **覆盖口径**：不能声称「19 部正史齐备」。准确说法是「19 部可检索，其中 14 部完整、
   5 部为上游残缺版本」。
3. **诊断（`/api/diagnose`）**：现在只会答「已收录的正文里确实没有这个串」，并在
   `planned_books` 里列出**尚未下载**的 9 部。它指不出「这部书**已收录但缺卷**」——
   搜「高阿那肱」（北齊書 卷五十 恩倖傳）走的就是这条路：答案是「正文里没有」，
   而真相是「北齊書 只到卷三十五」。这是本阶段暴露的**已知缺口**，不在原计划范围内。
4. **状态机**：`manifest` 的 `coverage_status` 量的是**篇名覆盖率**（须与
   `api/db.py:105-114` 口径一致），量不出「卷级完整度」；5 部现在仍是 `OK`，
   catalog 里也是 `recall_verified: true`（召回确实全过）。两者都不算错，
   但合起来会让人误以为「这些书是全的」。
