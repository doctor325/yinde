## 二、做了什么（§4 ~ §17）

### 2.1 卷级覆盖模型（任务一 / 十，§4 / §13）

新增 `scripts/pipeline/volume.py`（约 600 行，纯函数，不碰核心引擎）。

**判据是「两证据 + 一裁定」：**

- **证据一** `files.juan_prop` —— 文件头的 `#+PROPERTY: JUAN` 
- **证据二** `juans.label` —— 正文里的卷题
- **裁定** 卷的归属**以文件头为准**，卷题只负责**发现**卷号

为什么要分两证据：`juan_prop` 是编者写死的元数据，`juans.label` 是从正文里认出来的。两者一致时结论最硬；不一致时要能说出是哪一种不一致。`files.juan_prop` 单独用会漏（北齊書 卷三十六以后源头没有），`juans.label` 单独用会多认（把「前上十志啓」当成一卷）。

**明确排除了什么**（§13「不能只统计 file_count」）：

```
北齊書  36 个文件 = 35 卷   （_000.txt 是目録）
後漢書 125 个文件 = 120 卷  （目録 + 考證文件不是卷）
三國志  31 个文件 = 30 卷
魏書   116 个文件 = 114 卷
```

文件数一律不等于卷数。前端与诊断页显示的每一个卷数都是**卷号口径**，不是文件计数。

六个故障判据（都是 error，除非注明）：

| 码 | 含义 |
|---|---|
| `count-mismatch` | 登记的卷数与实测卷数不等，且无逐卷说明 |
| `out-of-range` | 收进来的卷号超出登记的卷范围 |
| `true-duplicate` | 同一卷号出现两次（`之一/之二` 分片不算） |
| `gap-unexplained` | 中间缺卷，且没有说明 |
| `over-expected` | 登记卷数超过通行本卷数 |
| `unwitnessed-file` | **warn**：正文文件既无卷题、也不在任何一卷的证据里 —— 语料没问题，是我们认不出 |
| `no-witness` | **info**：底本没有卷级证据，卷数是人工登记的 |

**逐卷豁免**：人能解释的缺口（魏書 卷一百五 被源文件拆成「之一…之四」，文件头认不出）记在 catalog 的 `volume_notes` 里，把 error 降为 info —— 但**不改 `declared == expected` 这个事实**。所以魏書显示 `113 / 114` 配「完整」，差额带 tooltip 说明。

### 2.2 三方数字，不许混用（任务一，§4 / §11）

| 名字 | 含义 | 用途 |
|---|---|---|
| `expected` | **通行本**卷数（外证，稳定） | 分母 |
| `declared` | **这部底本**有多少卷 | 说明「上游给到哪」 |
| `available` | **库内实测**卷号数 | 分子 |

`coverage_ratio = available / expected`，**分子是实测不是登记**。这条实现时踩过一次：第一版写成 `declared / expected`，那样会把「登记了却没数出卷」伪装成已收。测试 `test_coverage_ratio_uses_measured_not_declared` 钉住它。

三國志的 `30/65`：65 是通行本，30 是这部 WYG 底本的边界。两者的差**不是我们的解析故障**，是上游数字化只到卷三十。这句话必须出现在页面上，否则 30/65 会被读成「我们弄丢了 35 卷」。

### 2.3 书级六态（任务二，§5）

`manifest.merge_catalog()` 的状态判定按优先级：

```
failed  >  warning  >  partial  >  verified  >  imported
```

- `partial` 是 6.4 新增的第六态：**底本卷数 < 通行本卷数**，来自卷级审计，不是篇名覆盖问题。
- `partial` 与 `warning` **不能混**：`warning` 是「我们能修的解析问题」（篇名覆盖 < 0.90），`partial` 是「上游就是这样，我们修不了」。一部书可以同时是卷级 `complete` + 书级 `warning`（國語），页面上两块分开显示。

五部残缺正史**登记为 partial，不是 verified**（§5 逐字要求），跑出来逐部相符：

| 书名 | 应有 | 实收 | `declared` |
|---|---|---|---|
| 三國志 | 65 | 30 | 30 |
| 晉書 | 130 | 33 | 33 |
| 北齊書 | 50 | 35 | 35 |
| 隋書 | 85 | 49 | 49 |
| 北史 | 100 | 22 | 22 |

### 2.4 Book 与 Edition 分开（任务八，§11）

catalog 里增了 `editions` 段（一处登记、处处引用），每本书的 `editions` 一律是**列表**：

| id | 名称 | 来源 | 用在 |
|---|---|---|---|
| `wyg` | 文淵閣四庫全書本 | Kanripo `KR2a` 系列 | 15 部正史（史記除外） |
| `sbck` | 四部叢刊本 | Kanripo `KR2e` 系列 | 先秦文獻 |
| `tls` | tls 本 | 上游未标底本 | 史記 |

本阶段每部书只有一个底本，但结构上不假设如此 —— 将来给三國志补一个百衲本，只需在 catalog 加一条，页面不用改。

**实现时抓到的最严重的一个 bug**：写 `volume_coverage.json` 时用了
`dict(r["volume"], status=r["status"])`，把**卷级** status（complete/partial/unknown）
覆盖成了**书级** status（verified/warning/…），于是國語的卷级状态显示成 `warning`、
前漢書显示成 `verified`。改名 `book_status` 后修复。这个 bug 正好是本阶段存在的理由的
反面教材：两种读数一混，整份数据就失去了意义。

### 2.5 搜索结果四态（任务四五六，§7 / §8 / §9）

`search/diagnose.py` 新增单一判定点 `scope_status()`，返回四态之一：

| 状态 | 何时 | 页面标题 |
|---|---|---|
| `hit` | 有结果 | ——（正常结果） |
| `complete_no_hit` | 这部书收全了，语料里确实没有 | 所收版本内没有找到 |
| `partial_no_hit` | 这部书只收到某一卷 | **所收版本不完整，未收录的部分无从判断** |
| `not_imported` | 这本书还没入库 | 这部史书尚未收录 |

`partial_no_hit` 下**强制**带当前收录范围（`range_text` 或残缺清单），否则报错。
这不是文案要求，是数据要求：状态与范围必须来自同一次判定。

`not_imported` 的措辞是「**这不是「这本书里没有」，是这本书还搜不了**」——
主动否定「没有」这个词，而不是绕开它。

### 2.5b 「搜到了」的那一半（§28 的延伸）

§25 的四种情况**全部是「搜不到」时说什么**。做完四态之后发现还有另一半没管：

```
搜「高歡」限定《北齊書》 → 命中 1 段，页面一切正常，没有任何提示。
而《北齊書》只有 35/50 卷 —— 用户很自然会以为这 1 段就是北齊書里关于
高歡的全部。**结果是对的，结论是错的。**
```

这是最难发现的一类误读：没有任何东西出错，错的是用户读出来的意思。

补法（`diagnose.hit_scope()` + 前端 `partialBanner()`）：限定了单一史书**且有结果**时，
把该书的卷级范围随 `/api/search` 一起回，残缺时在结果上方画一条：

> ⚠ 所收版本不完整：《北齊書》的这部底本只收到 35/50 卷（缺 15 卷）。
> **下面的结果全部来自已收录的卷**；未收录的部分没有参与检索，
> 所以这不等于「北齊書里只有这些」。

两条自我约束：

- **只在限定了单一史书时给**。全库检索不给 —— 每次搜索都挂一条免责声明，
  说多了等于没说，还会让真正残缺的那 5 部失去分量。
- **只在残缺时画**。完整史书不给提示。同上。

代价：一次 `resolve_book` + 读一次内存里的卷级快照，**没有全表扫描** ——
正常检索路径的性能特征不变。

### 2.5c 前端渲染的测试缺口（补上的）

`scripts/site/check_engine.py` 的 14 项检查全是「Python 侧有什么，JS 侧是不是也有」
的对拍，**它们不渲染 DOM**。所以本阶段新写的 `volCells` / `volChip` /
`volumeTotalsCard` / `scopeCard` / `partialBanner` 在自动化里本来是**零覆盖**的：
模板字面量里漏一个引号、字段名写错渲染出 `undefined`，14/14 全绿而浏览器白屏。

新增 `tests/test_frontend_volcells.py`（18 条）：把 `app.js` 当模块载进 node
（掐掉末尾 `route(); headerStats(); footBooks();` 三行启动调用），用构造好的输入
调这几个函数，把产出的 HTML 拿回 Python 断言。判的是**产物**：

- 每一格必须正好 3 个 `<td>` —— `#/coverage` 表头 12 列，少一列整张表错位，
  而错位的表**看起来是正常的**，只是每列的意思都往后挪了一格。
- 任何一格都不许渲染出 `undefined` / `NaN` / `null` 字样。
- 「没有数字」的三种情形必须长得不一样（未提供／无卷级模型／有数字）。

这个测试写完当天就抓到一个真 bug：书 id 在库里查不到时，`scope_status` 会拼出
`《None》全文` —— `title` 是 `None`，页面 `esc()` 之后就是字面上的 `None`。

### 2.6 Recall Invariant（任务十一 / 十二，§14 / §15）

把召回断言从「条数相等」升级为**包含关系**：

```
expected_passage_ids ⊆ actual_passage_ids
```

存的是 `(book_id, file_name, row_first, row_last)` 而不是 `passage_id` —— rowid 只在
**这一个** history.db 里有效，重建库就会变；文件号 + 行号是从源文件直接读出来的，
只要源文件没改就永远指同一段原文。

- 只冻结每条的**前 8 段**：够抓住召回退化，又不会把「排序微调」判成失败（顺序不在包含断言的范围内）。
- 基线存在 `tests/search_cases/invariant.json`，与手写用例**分开**：那些是人想出来的，
  这个是跑出来的，节奏不同。
- `--freeze-invariant` 是唯一的冻结入口，且**必须先确认报告是绿的** ——
  把一次带 bug 的输出冻进去，那个 bug 就从此变成了「基线」，再也不会红。

新增 `tests/search_cases/coverage_scope.json`（13 条，A~F 六组）：A 完整史书必命中、
B partial 缺卷区、C 未导入 → `not_imported`、D 繁简（齊桓公/齐桓公）、E 篇名·卷名·国别、
F 全库范围的 partial。

**冻结结果（2026-09-14）**：373 条里冻了 **321 条**。剩下 52 条分三类，**都不是漏**：

| 类 | 条数 | 为什么不冻 |
|---|---|---|
| 负例（`must_hit=false`） | 37 | 本来就没有片段可冻 —— 冻一个空集等于什么都没说 |
| `cov-*` 四态用例 | 13 | 判的是**措辞**（`result_status` + 收录范围 + 不许断言「书里没有」）。判据走 `diagnose()`，这条路径不取片段表；要冻就得在四态分类器里**再跑一次检索**，那正是它 docstring 里警告的「第二套说法」 |
| 超长结果用例 | 2 | `nb-single-01` / `pagination-01`（基线里那 2 条「注意」）在分页审计那一步就返回了，走不到冻结那一行 |

**这条断言管什么、不管什么**，写清楚免得被当成万能保险：
- 管：**老结果不许消失**（召回退化）。语料只增不减，冻过的片段必须在以后每次跑里都还出现。
- 不管：反方向（一条 0 命中的用例以后命中了）不在射程内 —— 那由四态用例自己的
  `expect_status` 去守。一条断言管两头，两头都会松。

冻结入口**只留一处实现**（`freeze_run`）。这里删掉过一个 `freeze_invariant()`：
两个函数写同一个基线文件、各写各的 JSON 结构，那是两套基线，早晚后者覆盖前者。

踩到的坑值得记一笔：`datetime.now(timezone.utc)` 写在 `freeze_run` 的最后一行，
而 `timezone` 没有 import —— 373 条用例跑完、十几分钟过去，才在**最后一句** NameError，
结果全丢。现在写文件的那一段单独成函数，**开跑前先拿空表执行一次**，这类错在毫秒内就炸；
`tests/test_invariant.py` 专门钉住这次空跑（只加函数不加这次调用，等于什么都没防）。
顺带一提，那次崩溃在后台任务里被 `| tail` 管道吞成了 `exit code 0` ——
长任务不要用管道收尾。

§28 还有一条**机器判据**：摘要里不许出现**未被否定**的「正文中没有 / 史书中没有 /
书里没有 / 语料中没有」。判据不是「出现即禁止」—— 正确措辞里就带着它
（「这不是「这本书里没有」」），那是**否定**它，正是要的句子。所以看它前面 12 个字里有没有否定词。

### 2.7 `#/coverage` 页（任务三，§6）

**只加不改**：原有篇名覆盖口径一字未动，新增三列（已收/应有卷、卷覆盖率、卷状态）
+ 一块卷级总账。

这一页现在明确回答**两个不同的问题**，左右两栏分开：

- **篇名覆盖** —— 每卷正文有没有一个篇名可归。这是**我们的解析质量**，能修。
- **卷级覆盖** —— 这部书我们到底收了多少卷。这是**上游给了多少**，修不了。

混在一起的后果：5 部残缺正史的 79.5% 会被读成「我们的语料是残的」，
或者更糟 ——「史书里没有」。

`volCells()` 特意区分三种「没有数字」：`undefined`（我们没拿到，静态演示模式）
/ `known:false`（这部底本本来就不按卷分）/ 有数字。混成一格会让演示站上每本书
都显示「无卷级模型」，那是句假话。

### 2.9 性能：本阶段**没有**做什么（任务十五，§18 / §19 / §20）

**没有**提高 `MAX_HITS_PER_QUERY`（仍是 100000），**没有**改成 unlimited。
**没有**做 DB 层分页、块缓存、跨请求缓存。

这三项记为**已知性能债**（见第五节），本阶段不做，理由是它们与「覆盖自知」无关，
而任何语料/引擎的改动都会移动 6.3 的全部基线数字。

### 2.10 核心引擎：一行没改（任务十六，§21）

`search/engine.py` **未修改**。本阶段所有新逻辑都在
`scripts/pipeline/volume.py`（新文件）、`search/diagnose.py`（诊断路径，不在检索路径上）、
`scripts/pipeline/manifest.py`（管线）与前端。

诊断路径的代价：一次调用最多跑 3 次全表 `instr` 计数（本地实测约 0.35s/次）。
这是**诊断**的代价 —— 它只在用户想知道「为什么没有」时才跑，正常检索一行没改。

## 三、产品验收（§25）—— 四种情况逐条实测

用 `search/diagnose.py` 真实调用，输出如下（`book` 为书 id）。

### 情况一 · 完整史书 + 有结果 → `hit`

```
q=齊桓公  book=KR2a0007（前漢書）
→ result_status = hit
   正常命中：23 段 / 23 块（fts 路径）—— 没有搜不到的问题。
```

### 情况二 · 完整史书 + 无结果 → `complete_no_hit`（不是报错）

```
q=齊桓公  book=KR2a0019（陳書）
→ result_status = complete_no_hit
   《陳書》已收录的部分（36/36 卷）里没有「齊桓公」（0 段）。尚未收录的正史还有 9 部
   （隋唐 2 部、五代 2 部、宋 3 部、元 1 部、明 1 部；最早的缺口是《舊唐書》，
   一直到《明史》）—— 若该词属于这些书的范围，搜不到是覆盖范围问题，不是检索问题。
```

### 情况三 · partial 史书 + 无结果 → `partial_no_hit` + **显示当前收录范围**

```
q=齊桓公  book=KR2a0021（北齊書）
→ result_status = partial_no_hit
   《北齊書》已收录的 35 卷里没有「齊桓公」（0 段）。但《北齊書》的这部底本只收到
   35/50 卷（底本收至卷35，通行本共 50 卷）—— 未收录的部分没有参与检索，
   所以这不等于「北齊書里没有」。
```

### 情况四 · planned 史书（明史）→ `not_imported`（不是「正文中没有」）

**接口侧（实测）**：

```
q=朱元璋  book=KR2a0038（明史）
→ result_status = not_imported
   《明史》尚未下载，还没进检索范围（全书 332 卷）—— 这不是「这本书里没有「朱元璋」」，
   是这本书还搜不了。已收录 19 部，未收录 9 部。
```

**接口答得对，不等于用户问得到 —— 这是本阶段最后改的一处。**

验收时发现：`not_imported` 这句话在浏览器里**没有入口**。

- 搜索页的史书下拉只列 `/api/books` 的 19 部在库书；
- 提问页压根不带 `book`（`doAsk()` 只发 q/mode/text）；
- 手写 `#/search?book=明史` 会撞上 `/api/search` 的 400 ——
  `engine.resolve_book` 只认库里的书。**那是 engine 的本分，§21 明令不动它**，
  该改的是调用方：这本书不在库里，本来就不该送去检索。

于是用户无论怎么点，看到的都是「在已经收录进库的 19 部史书里没有…」，
而他问的恰恰是那 9 部里的一部。这正是 §28 要消灭的误解。

改法（**只动前端，引擎一行没碰**）：

- 史书下拉多一组「尚未收录（搜不到）」，数据来自 `/api/catalog` 的 `planned`
  （演示模式取不到目录，这一组不画 —— 真实书名仍然一个都不进公开产物，§22）；
- 选中这一组的书时**不去请求 `/api/search`**，直接走 `/api/diagnose`，并复用空结果那套
  渲染：四态标题「这部史书尚未收录」、收录范围卡、逐层排查都在同一处，
  不为这条路另写一套说法；
- 判据只有一处（`isPlannedBook`）。判错的方向是不对称的：判成「在库」→ 用户看到错误框，
  判成「未入库」→ 用户看到「这部史书尚未收录」。后者才是真话。

验证：`tests/test_frontend_volcells.py` 用 fetch 桩把这条路端到端跑起来
（桩对任何非 `/api/diagnose` 的请求直接抛错 —— 一旦有代码把计划书送去搜索接口就会红），
并钉住判据真值表：计划书 → true；在库书 / 空 id（「全部史书」）/ 拿不到目录 → false。

**一处自纠**：我最初还判过一次「未导入的书没在空结果里说出来」，查下来是**错的**。
不限史书时，`scope.detail` 与收录范围卡早就写着「全库 19 部：5 部底本残缺、9 部尚未入库
—— 无法断言『全部史料里都没有』」，四态也正确地给 `partial_no_hit`
（库里本就有 5 部残卷，「全都没有」从库的层面就断言不了）。我加的那一行是重复的，删掉了。

### 全库范围（无 `book` 过滤）

```
q=朱元璋  book=None
→ result_status = partial_no_hit
   在已经收录进库的 19 部史书里，没有「朱元璋」（0 段）。其中 5 部底本本身就残缺
   （《三國志》30/65 卷、《晉書》33/130 卷、《北齊書》35/50 卷、《隋書》49/85 卷、
   《北史》22/100 卷）……
```

§28 的总原则在这里落地：**宁可明确告诉用户「我的史料不完整」，也不能让用户误以为「史书中没有」。**

## 五、已知限制与性能债（如实记录）

### 5.1 本阶段没做的性能优化

DB 层分页、块缓存、跨请求缓存 —— **本阶段明确不做**，但记在这里，因为它们是真实存在的债：

- `MAX_HITS_PER_QUERY = 100000` 未变，超大命中集仍会一次性装进内存。
- 诊断路径一次调用最多 3 次全表 `instr` 计数（约 0.35s/次，本地实测）。
- 跨请求无缓存：同一查询第二次仍然是全量重算。

### 5.2 「自然语言提问」视图未升级到四态

`#/ask` 的空结果仍说「**语料中**没有找到相关史料」。

**不算 §28 违规**：它说的是「语料中」，不是「史书中」/「正文中没有」——
措辞本身已经是正确的框定。§25 的四种情况验收的是**检索**路径，不是提问路径。

但仍是一个缺口：提问视图**不显示收录范围**。已做的补救是在空状态加了一句
「这句话说的是**我们的语料**里没有，不是「史书上没有」」并链到 `#/coverage`。
**未做**的是把 `result_status` 接进 `/api/ask` 的响应 —— 那要动 `search/question.py`，
超出本阶段范围，且会移动 6.3 的提问基线。

**更尖锐的一处（实测 2026-09-14）**：问题里出现的**书名**不被当作检索范围。
问「明史里有齐桓公吗」，实体层抽出的是 `齊桓公`，返回的是史記与春秋左傳里的
18 件事 —— 全书唯一被识别出的专名是人物，`明史` 三个字被无声丢掉，
用户不会得到「明史还没收录」这句话。

按上面的分流，`book=明史` 这条路（情况四）已经能走通；**走不通的是「在一句话里点名一部书」**。
要补它得在提问链路上做书名识别（语料目录里 28 个书名是现成的，`diagnose` 也已经在回
`planned_books`），但那会动 `question.py` 与 6.3 的提问基线，**本阶段不做**，
记在这里作为下一步的第一个候选。

### 5.3 上游残缺无法在项目内修复

5 部 partial 正史 + 上游残缺的 3 部未导入正史，缺口在 Kanripo 侧。
本项目能做的是**说清楚**，不是补齐。补齐的路（找别的底本 / 自己数字化）不在本阶段。

### 5.4 卷级模型只覆盖有卷的史书

先秦四书（以篇为单位）没有卷级模型，走 `witness: none` 分支。
将来若要给它们做“篇级覆盖”，是另一套模型，不是这一套的扩展。
