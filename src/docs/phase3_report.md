## 2. Result Block 算法：一个命中如何变成一段史料片段

一句话：**命中点不动，决定的是它前后各"包"多大一段，包到史料自己换段为止。**

```
① 取全命中
   命中仍由 FTS5 定位（trigram / bigram / LIKE，与第二阶段同一条路）。
   但片段要先看全命中才能正确合并与计数，所以这里不分页 —— 一次拿到
   全部命中行（受 MAX_BLOCKS_PER_QUERY=600 段封顶保护），按
   (row_no, seq) 排成阅读顺序。

② 每条命中各自向外扩
   从命中行向两侧逐行读邻居（窗口按需生长，最多 600 行），每读一行问一次
   「能并进来吗」。判定全部走 _can_take() 这**一个函数**——扩展、展开、
   可达范围测算三处共用同一个判断，避免规则漂移（这是本阶段踩过的坑，
   见 §7 第 2 条）。停止条件是下面四样：

     kind != 'passage' 的解析器行  → 透明穿过，不进正文，也不打断
     layer 变了                    → 停（正文绝不与括注/序跋/附录混排）
     段落键变了                    → 停
     # src: 段落号变了             → 停（仅当该行没有更可靠的结构字段时）

③ 段落键：section → subsection → ab → # src: 前两级
   依次取第一个有值的。键不同即不同段；**「有键 ↔ 无键」也算变化**，
   宁可少并一点，也不把两段史料缝成一句（任务书 §十：宁可短，不可臆造）。

④ 合并相邻命中
   两条命中扩出来的区间若重叠或首尾相接，就合成一个片段；合并后重算可达
   范围。同一次查询里同一片段只出现一次，不重复计数。

⑤ 切片
   按显示长度上限（target_chars / max_passages / max_chars）定片段规模，
   超了就截断并记下「还能继续读」，够就不记。最后分页返回。
```

**三种显示长度**（`mode`，默认 `standard`）：

| mode | 目标字数 | 单段上限 | 最多并几条 | UI 名 |
|---|---|---|---|---|
| `short` | 120 | 260 | 12 | 简短 |
| `standard` | 420 | 900 | 40 | 标准 |
| `long` | 1200 | 2600 | 120 | 完整 |

**「还能继续读」怎么判定**：被长度上限截断 → 显示按钮；已经读到史料自己的段落开头/末尾 → 不显示。
两者由 `_reach_edges()` 用**同一套边界规则**沿片段两端探到底后区分，不是「剩余行数 > 0」这种粗判。
前端据此决定按钮出不出，点进去确实是空的情况不会发生。

**任务书 §三 红线逐条对照**

| 红线 | 做法 |
|---|---|
| §三.1 不得 AI 生成正文 | 片段正文 = 所列 passage 的 `text_orig` 依序相接，无一字增删 |
| §三.2 不得写死「前5后5」 | 边界由 `book/file_id/row_no/seq/section/subsection/layer/kind/pb` 结构字段决定 |
| §三.3 HistoryLibrary 零写入 | 见 §6 |
| §三.4 不重新解析原始语料 | 只读第一阶段已入库的 `passages/files/books` |
| §八.4 不判断注者 | 片段带 `layer` 字段原样透出，前端只作如实转述，不推断韦昭/高诱 |
| §九 索引/展示分家 | 索引吃 `normalized_text`，展示用 `text_orig` |
| §十 不加标点、不润色 | tls 的 `¶` 与 `<pb:>` 是原文，照留；`# src:` 是解析器行，永不进正文 |
| §十六 不解释 tls | 沿用第二阶段规则原样显示，缺失字段一律「暂无」 |

## 3. 真实案例：命中 → 扩展 → 最终片段

三个基准词在真实库上的实测（各模式片段数，已由 `test_result_block_real.py` 钉住）：

| 查询 | 原始命中 | 简短 | 标准 | 完整 |
|---|---|---|---|---|
| 齐桓公 | 96 条 | 26 段 | **23 段** | 18 段 |
| 管仲 | 102 条 | 43 段 | **31 段** | 26 段 |
| 黄帝 | 163 条 | 29 段 | **23 段** | 18 段 |

96 条孤立短句 → 23 段可连续阅读的史料片段，这就是本阶段要做的事。

**实例一：`齐桓公`，标准模式**

```
命中 passage   66617（史記 齊太公世家，file 94 内）
               原文：「…桓公於是始霸…」单句一条，自身只有十几个字
扩展            向前 40 行 / 向后 40 行内，逐行按 _can_take 判定；
               遇 layer 变化或段落键变化即停
最终片段         block_id = 94:1360:1285
                n_passages = 7 条记录 → n_chars = 151 字
                pb_first/pb_last 给出跨页范围
                more_after = true（确实还有下文可续读）
```

**实例二：`管仲`，标准模式**

```
命中            多条（史记、國語等分散在多个文件）
扩展 + 合并     同一文件内相邻的两条命中扩展后区间重叠 → 合成一段
最终片段         31 段；最短 9 字、p50 104 字、最长 973 字
                 p50 从第二阶段的「一条十数字」提升到「一段百余字」
```

**实例三：`黄帝`，完整模式**

```
最终片段         18 段；p50 461 字、最长 1585 字
                 较长片段一律能用「← 继续向上文 / 继续向下文 →」再续读
```

**续读实测**（`tests/perf_phase3.py` 里真实点一次）：

```
齐桓公 段「94:1360:1285」再读 40 条 → 实得 40 条   23ms   ★ 无重叠、仍是原文
```

**片段内容不变量**（真实语料上 12 项断言，全部通过）：
正文逐字等于所列 passage 的 `text_orig` 相接 · 无 `# src:` / `# dating:` 等解析器行 ·
每段必有真命中 · **绝不跨文件** · **绝不跨层** · 阅读顺序递增 · 翻页无重复无遗漏 · `block_id` 唯一。

**如实说：p95 超了 300ms**（管仲 398ms、王 375ms），p50 基本在线内。
这不是「挑个好看的数字报」，也不是组装逻辑有抖动，原因见下。

### 4.3 关于这批数字，交付方需要知道的三件事

**① 这台机器在本次会话中断崖式降速，后半程全在慢档。**

同一份代码、同一份数据、同一台机器，会话中各轮的对比基线就说明问题：

| 测量时刻 | P2 逐条（齐桓公） | P2 超热词「之」 | P3 标准（管仲） |
|---|---|---|---|
| 会话前期 | 4.9ms | 203ms | 151ms |
| 会话后期 | 6.2ms | **391ms** | **242ms** |

P2 那条路径本阶段**一个字都没改**，它却慢了近一倍 —— 说明是主机环境的整体降速，
不是第三阶段的代码问题。已查：交流供电、电源方案「平衡」、非电池。符合持续算力负载下的整机降频特征。

**结论**：§4.1 的 min 列是该机在正常状态下能跑出的最快值（115–150ms 量级）；
§4.2 的 p95 是降级状态下的数，**不是**组装算法的固有抖动。请在正常状态的机器上复跑
`python tests/perf_phase3.py` 确认。

**② 组装成本 CPU-bound，与 P2 的差距稳定在 110–250ms。**

交错 A/B 实测（同一代码路径连续跑）：

```
P2 逐条  4.3 4.4 4.2 4.3 4.4 4.3 4.2 4.3 4.3 4.2   → p50 4.3ms
P3 标准  123 121 119 124 122 126 120 118 125 121  → p50 122ms   （+117ms，+2740%）
```

用 `time.process_time()` 单独量过：CPU 时间与墙钟几乎相同（如管仲 standard：CPU p50 375ms / 墙钟 p50 378ms），
**没有 I/O 等待或锁竞争**，纯粹是算力。这 100–250ms 换来的是「一次给全上下文」而不是逐条翻。

**③ 请求日志曾伪装成性能问题。**

基准脚本原本把 `Handler` 的逐行请求日志同步写 stderr，「王/完整」因此多出约 80ms 墙钟时间
（302ms → 223ms），一度看起来像超了标。已在两个基准脚本里就地抑制并注释说明；
服务日常运行日志照常打印。**这不是服务端成本，但会污染任何用 HTTP 打点的基准。**

### 4.4 时间花在哪（profile 结论）

对 `管仲/standard` 做 cProfile（5 次调用平均）：

| 环节 | 占比 | 说明 |
|---|---|---|
| `_FileCache.segments()` | ~60% | 每个文件读全部源出行并逐条 `json.loads` + 正则 |
| `_seg_of()` | ~15% | 行号落区间判定 |
| SQLite `fetchall`/`execute` | ~26% | 行窗口本身 |

**这是个可优化点，但本阶段没做**：`segments()` 每次要把一个文件里所有 `# src:` 行拉进 Python
（史記最大的一份有 2,611 条），每条都要 JSON 解析一次，只为取出 `section_ref` 的首两级。

我试过把过滤下推给 SQL（`LIKE '%"section_ref"%'`），**逐文件比对确认结果完全一致（4,815 个区间）**，
但微基准显示**没有收益**（file 95：旧 21.5ms / 新 22.5ms；file 94：旧 6.97ms / 新 6.84ms），
因为那些文件里 `# src:` 行本来就占多数，真正贵的是那 2,611 次 JSON 解析。

**已回退该改动** —— 没有收益就不该留这段额外复杂性（多一条 SQL 谓词、多一处「只多不少」的隐含假设）。

若第四阶段要动性能，正道是**在建库时把 `src_paragraph` 派生字段落到表里**（属于 HistoryAI 自己的派生数据，
不碰原始史料），让检索时直接读一个短字符串，省掉整个 JSON 解析。预计能把组装从 ~130ms 压到 ~60ms 量级。

## 7. 已知问题

### 7.1 哪些史书仍然难以自动确定自然段

资料库只有两个版本家族，难度天差地别：

| 家族 | 记录数 | 层级分布 | 自然段判定难度 |
|---|---|---|---|
| **tls**（Kanripo） | 183,820 | main 163,461 / structure 19,804 / appendix 555 | **容易**。原文本来就以 `¶` 把每个句子分开，句界是原文自带的，`# src:` 又给段号，几乎不用猜 |
| **SBCK**（四部丛刊） | 41,002 | main 21,476 / **commentary_candidate 17,347** / structure 1,710 / preface 286 | **难**。连续文本，正文与行内括注混排，**42% 的记录是待确认括注** |

**SBCK 是真正的短板**：它没有 `¶`，只能靠第一阶段判定的 `layer` 切分。好在 `layer` 边界已被
证明是可靠的停点（`test_block_never_crosses_layer` 在真实语料上全过），所以系统宁可把括注单独成段，
也不去猜「这段括号是不是注」。**这是设计选择，不是缺陷**——但它意味着 SBCK 书里的片段可能偏短、偏碎。

### 7.2 哪些边界规则存在歧义

1. **`# src:` 段号与结构字段谁优先** —— 现取「结构字段优先，`# src:` 只在没有结构字段时才作证据」。
   原因是左傳/尚書的 `# src:` 行比 `section` 更细，用它会切碎阅读单元。这是实证选择，不是唯一正确答案。
2. **「有键 ↔ 无键」算不算变化** —— 取严格口径（算变化）。实测严格与宽松两版在真实语料上产出的
   **片段数、长度、定位完全相同**（齐桓公 26/23/18、管仲 43/31/26、黄帝 29/23/18，两版一致），
   既然效果相同，就取不会读串的那个。
3. **`_src_paragraph` 的解析形态** —— 只认开头「≥2 级点分数字」，`'ZUO Xi 17.5.6'` 这种前缀里夹了
   非书名词的一律视为无证据。**这是保守取舍**：宁可少切一刀，不可臆造段号（§十）。
4. **`section_ref` 形态不统一** —— 库里同时存在 `'004.41.2, ed. …'`、`'SHIJI 28.70.3 …'`、
   `'ZUO 17.5.6 …'`、`'1.1; tr. Karlgren …'` 多种写法，目前靠正则兜住。新语料若有新形态，
   需要人工确认后再扩规则，**不能靠猜**。

### 7.3 哪些搜索结果仍然可能偏短

- **SBCK 行内括注**：`layer='commentary_candidate'` 共 17,347 条，平均 15 字，**最短 3 字**
  （如 `(也)` `(燎)`，见 pid=320 `(也)`）。它们的 `text_orig` 字面以 `(` 开头，层级边界就在前后，
  因此 `more_before=false, more_after=false` 是**正确**的——真的没东西可续。
  本阶段为这类卡片加了左侧浅紫标记 + 「（原刊括号内容 — 是否注文待人工确认，系统不作正文判定）」
  说明行，避免看起来像「检索结果不全」。
- **结构键频繁变化的书**：每遇篇/章标题就停，小节切得密的书片段会短。
- **首条 `# src:` 之前的引子行**：不属于任何段号区间（`_seg_of` 返回 -1），不会被并进任何片段。

### 7.4 哪些情况下可能过长

- **`long` 模式**：上限 2600 字、最多 120 条记录，实测最长片段 **2288 字**（管仲）。
  连续读 2000+ 字文言不是所有人都想要——但这正是「完整」模式存在的原因，默认是 `standard`。
- **tls 大段无分节的文本**：若某书通篇没有 `section`/`# src:` 变化，扩展会一直读到长度上限才停。
  有 `max_chars` 硬顶兜底，不会无限。
- **相邻命中密集处**：多条命中扩展后合并成一大段，长度是叠加的。已由 `max_chars` 截断并标记可续读。

### 7.5 是否需要第四阶段做「事件级史料聚合」

**我的判断：需要，但应该先补三件小事，再考虑事件聚合。**

**支持做事件聚合的理由**：本阶段已经把「一个命中 → 一段可读史料」做扎实了。但用户真正的历史问题
（「城濮之战是怎么回事」）会横跨**多个文件、多个史书**，现在的片段被硬边界锁死在单文件单层内
（`test_block_never_crosses_file` / `never_crosses_layer` 把这条钉死了）。这正是任务书 §三十四
描述的下一阶段：检索多个史料片段 → AI 基于史料回答。

**但先补这三件小事**（都是本阶段暴露出来的具体问题，成本低、收益直接）：

1. **性能**：建库时落一个 `src_paragraph` 派生字段，省掉 `segments()` 每次 2,611 次 JSON 解析
   （见 §4.4，预计组装成本能砍一半）。
2. **SBCK 括注的最终裁决**：17,347 条 `pending_commentary` 还挂着「待人工确认」。
   事件聚合一旦开始混排多来源，这批未定性的记录会变成噪音来源。要么人工过完，要么明确排除在聚合之外。
3. **`section_ref` 形态归一**：目前四种以上写法靠正则兜。做跨书聚合前应该先把段号解析成
   统一结构，否则跨书对齐无从谈起。

**明确不建议**把事件聚合直接做成「AI 自动判断史料段落」——任务书 §八.4 / §二十九 划的红线
（不猜注者、不自动断句、不自动判断段落）在第四阶段仍然应该成立，聚合的**依据**必须来自
可解释的结构信号和要求书里明写的规则，而不是模型输出。

## 9. ⚠ 交付方需知：一处 API 契约变更

**`GET /api/search` 未带 `level` 时的默认返回，从「逐条命中」改成了「史料片段」**（`level=block`，`mode=standard`）。

- 影响：老调用方读的是 `items`（`total` = 命中条数 96），新默认返回的是 `results`（`total` = 片段数 23）。
  要拿回第二阶段的形状，显式带 `level=passage` 即可，该路径已实测确认逐字未变。
- 本仓库内适配：`tests/test_search_api.py` 的 2 例按新默认值断言，并新增 `test_level_passage_backward_compatible`
  钉住老路径；`tests/perf_phase2.py` 的 5 处检索显式带 `level=passage`，注释写明原因。
- **判断依据**：任务书 §一 要求「让一个搜索结果从单条短 passage 升级为完整史料片段」，前端是唯一调用方
  且已一并重写，逐条路径仍完整可用、仍有前端入口（每张片段卡片的「定位到命中句 · 单条原文」）。
- 若交付方希望默认值反过来：改 `api/main.py` 里那一处 `level` 默认值即可，前后端各一行。

**新增端点**：`GET /api/blocks/{passage_id}?direction=before|after|both&count=&before_passage_id=&after_passage_id=`
—— 按需续读，绝不跨层、绝不越锚点另一侧；未知 id → 404，非正文 → 400，方向非法 → 400。

## 11. 浏览器验收路径

1. 首页搜「齐桓公」→ 默认「标准」长度，应看到 **23 段**可连续阅读的史料片段，不是 96 条孤立短句；
   页面顶部写明「共 23 段史料 · 原始命中 96 条，已按上下文合并为完整片段」。
2. 切「简短 / 完整」→ 段数应变成 26 / 18，同一段内容随之变长变短，**正文永远是原文**。
3. 找一段带 `继续向下文 →` 的卡片 → 点它 → 底部淡底纹处续上新原文，片段计数跟着涨；
   读到末尾后按钮变「已读到本段末尾」并禁用。
4. 确认**没有任何一段跨越正文/括注边界**；带左侧浅紫标记的卡片是原刊括注，卡片上有
   「是否注文待人工确认」说明。
5. 点「定位到命中句 · 单条原文」→ 仍能回到第二阶段的逐条详情页与上下文。
6. 复跑 `python tests/perf_phase3.py` 与 `python -m unittest discover -s tests`。
